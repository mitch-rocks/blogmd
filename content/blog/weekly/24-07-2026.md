## Context

*Assume a 60-2 tooth trigger wheel*
As a worst case scenario, when a standard 4-stroke petrol car engine is running at 10,000RPM, the following is required to be handled by the engine management system (ECU):

* ECU receives 580,000 crankshaft tooth events per minute.
* ECU receives 9,666 crankshaft tooth events per minute.
* This leaves a ~105us window to handle each tooth event before the next one arrives.
* These events are decoded into engine position, speed, and acceleration
* Ignition/injector schedules are recalculated and registered.

<hr>

## Introduction

The above section details the time constraints inherent with scheduling injector/ignition outputs at high RPM. In addition to output triggering there are many other parts of the firmware that are required to be serviced, for example communication with the tuning software, reading sensors, updating table output values, updating functions, handling CANbus communication, plus much more. As the functional complexity of an ECU's firmware grows, deterministic output triggering and event handling should always remain the highest priority.

![Trigger Output Flow](/static/image/trigger_to_output_flow.png)

Following the above image logically, you can assume that the output accuracy of one subsystem is dependent on the output accuracy of the subsystem/s that is depends upon. Bad data in equals bad data out, and this pattern continues down the chain.

Without deterministic output triggering (the output has jitter), the ECU is incapable of triggering hardware at the target time, and depending on the application, could be catastrophic to engine hardware both instantaneously and over time.

Deterministic output triggering is dependent on the time-critical processing of data such as trigger wheel teeth. If the duration of decoding a tooth event, and rescheduling outputs is greater than the time between teeth, then the ECU will be rescheduling outputs with data that doesn't completely represent the current state of the engine, and while the errors introduced here wouldn't be substantial, and users would likely not notice any change in how their engine is operating, the ECU still technically becomes "out of sync" with the engine.

## Scheduling System Design

My ECU's scheduling system implements tasks in a priority heirarchy. Some tasks that are *very* time critical operate within special dedicated schedulers, for example *HardwareScheduler*. Tasks that are still time critical but are long-running run within SoftIRQ. Tasks that are not time sensitive or run continuously are executed within the main loop. Each priority level is capable of preempting any task running within any level below it. 

This is called **Heirarchical Preemption**.

![test](/static/image/priority_heirarchy_image.png)

The below sections detail the exact operation and tasks that each priority layer handles, and in what contexts. Note that a lot of classes implement a `tick(TickEventType)` method. This method is called to allow an instance of a class to perform the update logic related to a particular event type. TickEventType is just a normal enum, see here:

```
enum class TickEventType : uint8_t {
    MainLoop,
    EngineTDC,
    EngineCycle
};
```

This ticking mechanism is necessary to allow certain functions (ECU functions) to be ticked upon specific events occurring. For example, a soft RPM limiter function will need to be updated each engine cycle event to cut fuel and/or ignition for one or more cylinders on a per-cycle basis.


### Mainloop

Once the ECU has performed all initialisation functions, it enters the main loop. 

The main loop is literally just a `while (true) { ... }` loop who's entire purpose is servicing tasks that aren't necessarily time critical, and can be serviced on a "as frequently as possible" basis. The list of routines serviced by the mainloop will eventually include:

| Routine | Description | TickEventType? |
| :-----: | :---------: | :------------: |
| SensorManager::tick(TickEventType) | Iterates over ALL Sensor (and subclass) instances, reading analogue values from hardware, calculate voltage, calculating the output value. | MainLoop |
| TableManager::tick(TickEventType) | Iterates over ALL Table instances, fetching sensor output values and calculating a new output value. | MainLoop |
| FunctionManager::tick(TickEventType) | Iterates over ALL Function (and subclass) instances, each function is essentially a real-time scheduling modifier. | MainLoop |
| Serial Communication | Handles one full tuning software message/command each iteration of the main loop | - |

### SoftIRQ

SoftIRQ is an interrupt-driven task servicer, who's entire purpose is to service certain time-critical tasks that are too long running to be executed in high-priority IRQs. SoftIRQ is built on top of a single interrupt that has been allocated a lower NVIC priority. This allows it to preempt anything running in the main loop but nothing else. 

SoftIRQ isn't used to "schedule" tasks in a sense, when a task is required to be serviced by SoftIRQ, we configure SoftIRQ to tell it what tasks needs servicing using bit masking, then configure the set-pending bit to 1, which will then execute the SoftIRQ ISR as soon as there is no higher-priority ISR already running.

The list of routines serviced by the SoftIRQ include:

| Routine | Description | TickEventType? |
| :-----: | :---------: | :------------: |
| FunctionManager::tick(TickEventType) | Iterates over ALL Function (and subclass) instances, each function is essentially a real-time scheduling modifier  | EngineTDC,<br>EngineCycle
| DecoderManager::process_queue() | Processes all tooth edge events in the ToothEventQueue, updates EngineState.  | - |
| InjectorScheduler::reschedule() | Calculate new on/off timestamps for all InjectorOutput instances, update in HardwareScheduler | - |
| IgnitionScheduler::reschedule() | Calculate new on/off timestamps for all IgnitionOutput instances, update in HardwareScheduler | - |
| CANManager::tick() | Class not implemented yet. Theoretically would process frames in CANFrameQueue. All or batched. | - |
| DeviceManager::tick() | Class not implemented yet. Theoretically would handle CAN/other time-sensitive messages. | - |


### HardwareScheduler

HardwareScheduler is a lean class implementation that allows other areas of the firmware (InjectorScheduler/IgnitionScheduler) to schedule output changes to specific GPIO pins used for triggering injector or ignition outputs. Each pin has two channels, one for setting the pin (turning it on), and one for clearing the pin (turning it off). That is the entire purpose of the HardwareScheduler, abstracting away scheduling of pin state changes for multiple pins and handling them with the shortest `interrupt -> state change` path possible.

The microcontroller that we are using does not have any compare-output timers, so we are limited to triggering output purely through a software handler for an interrupt (ISR). Setting/clearing pin state is implemented using our incredibly lean functions from our hardware abstraction layer (HAL). When overclocked, the MCU is capable of changing the state of a pin within ±1.5 microseconds of the target timestamp.

The interrupt that HardwareScheduler uses is assigned the second-highest NVIC priority, allowing it to preempt Mainloop and SoftIRQ tasks in order to change the state of an output. This is necessary for deterministic output.

### Crankshaft/Camshaft Tooth Interrupts

Interrupts generated from crankshaft/camshaft sensors picking up teeth on the engine's trigger wheels is the upmost priority. These events are the origin and single source of truth for the engines current position, speed, and acceleration. 

Referring back to the pipeline that processes these teeth interrupts into ignition/injector output, if our data acquisition (a timestamp) for these tooth events aren't accurate, then we essentially poison the rest of the processing pipeline, eventually leading to incorrect trigger outputs, even if all of our math and algorithms are correct.

For this purpose exactly, interrupts handling the capture of tooth timestamps operate at the highest NVIC priority. They record the current timestamp as the time that the tooth was detected. a ToothEvent struct is instantiated, containing this timestamp and the state (on or off) of the pin that triggered this interrupt. This is pushed to the specific ToothEventQueue for either the camshaft or crankshaft sensor. Once this is done, the tooth decoder task is marked as 'TODO' via SoftIRQ and then the ISR returns.  

### Conclusion

Hopefully this blog post has educated you on how it is possible to design a scheduling system for a relatively complex application and environment using multiple subsystems servicing specific tasks/routines, each interoperating seamlessly (and indirectly) with eachother using **heirarchical preemption**. 

High priority ISR's are used solely for capturing an event and scheduling delegated processing, as well as for handling the scheduled state changing of an output. Low-priority ISR's handle the execution of time-sensitive, delegated math/processing/servicing tasks, while still being able to be preempted by high priority ISR's. The mainloop simply runs whenever there is now high or low priority ISR running at all, and services these background tasks at an "as often as possible" basis.
